# FIRE Navigator

日本の税制・社会保険料・NISA/iDeCo等の制度を反映した、手取りベースの資産形成シミュレーションエンジン。
ローカルのJSONファイル（`data/plan.json`）とブラウザ上のダッシュボード（Flask + Chart.js）を
入出力UI（View）として使い、計算のSource of TruthはPythonエンジン側に置く
（「Engine First」という設計思想。詳細は `docs/` 配下の設計書を参照）。外部サービスへの接続は
一切不要で、完全にローカルだけで完結する。

## 現在の状態

MVP定義とロードマップ（`docs/FIRE_Navigator_MVP定義とロードマップ.md`）のSprint1〜10に加え、
`docs/FIRE_Navigator_旧ドラフトとのギャップ分析_追加要件定義.md`で確定した追加要件
（資産クラスの拡張性・Master/ダッシュボード・Projection Engineの月次化・譲渡税/取得原価管理・
資産配分比率の可変対応/月次リバランス・教育費/大型一時支出）が完了しています。

- 決定論的シミュレーション（税引後キャッシュフロー、NISA/iDeCo等の口座別配分、取り崩し、公的年金の繰上げ/繰下げ）。
  内部的には**月次ループ**で計算し（Sprint12 月次化）、年末時点の集計を`yearly_projections`、
  月次明細を`monthly_projections`としてそれぞれ`SimulationResult`に保持する
- **譲渡税・取得原価管理**（Sprint13）: 課税口座（TAXABLE）からの取り崩し時、平均取得原価方式で
  実現益を算出し譲渡税(20.315%)を課税する。NISA等の非課税口座は対象外。口座（`accounts`）の
  取得原価（任意入力）でシミュレーション開始時点の含み益/含み損を指定できる（未入力の場合は
  残高と同額、つまり含み益ゼロからのスタートになる）
- **資産配分比率の可変対応・月次リバランス**（Sprint13）: 年齢別の目標配分比率（`allocation_policy`、
  任意）をプラン全体で1つ持ち、毎月ドリフトをチェックして新規拠出で優先的に埋め、
  埋めきれない分は非課税口座を優先して売却→再投資する。Monte Carlo/Historical Engineも
  この目標配分比率でその時点の資産クラス別リターンを加重合成する（固定比率で合成しない）
- **教育費・単発支出**（Sprint14）: 子供の年齢帯に応じた教育費（`education_expenses`、任意）を
  毎月の支出に自動加算する。車・旅行・住宅購入等の単発支出は支出（`expenses`）に統合されており、
  `kind`で区別する（該当行のみ指定した年月〈プラン開始時から/年齢で指定/日付で指定〉に全額を
  一括計上する）
- マイルストーン到達判定・感応度分析（口座期待リターン増減×インフレ率）
- モンテカルロシミュレーション（月次相関考慮サンプリング）・ヒストリカルバックテスト（過去データ）
- Master的な要約入力ビュー（年金条件・目標資産）・ダッシュボード（逆算による追加可能額・資産枯渇年齢）
- 回帰テスト（`tests/regression/`）で保護された計算ロジック

## セットアップ

### 前提

- Python 3.13

### 手順

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

外部サービスのアカウント登録や認証キーの発行は不要。上記だけで実行できる。

## 使い方

### 全部まとめて実行する（推奨）

**Finderからダブルクリックで実行する場合**: リポジトリ直下の `シミュレーション実行.command` を
ダブルクリックする。初回はmacOSのセキュリティ設定でブロックされることがあるため、その場合は
`シミュレーション実行.command` を右クリック→「開く」を選び、表示される確認ダイアログで
「開く」を選択する（一度許可すれば以降はダブルクリックで実行できる）。ローカルWebサーバー
（Flask）がバックグラウンドで起動し、既定のブラウザでダッシュボード（`http://127.0.0.1:5001/`）
が自動的に開く。

ダッシュボードの左側フォームで口座・収入・支出・配分方針・子供/教育費等を入力し（行の追加/削除
ボタンあり）、「保存」で`data/plan.json`へ書き込み、「シミュレーション実行」ボタンで決定論的
シミュレーション・感応度分析（モンテカルロ/ヒストリカルバックテストは任意でチェックを入れた
場合のみ、時間がかかるため既定では省略）を実行し、右側にKPIカード・月次詳細・純資産推移
グラフ・モンテカルロ/ヒストリカルの分位グラフ・感応度分析グリッドを表示する。入力内容は
`data/plan.json`にファイルとして保存されるため、次回起動時も前回の入力が復元される。

**ターミナルから起動する場合**:

```bash
PYTHONPATH=. python3 web/app.py
PYTHONPATH=. python3 web/app.py --port 5050   # ポートを指定
```

### CLIから実行する（デバッグ用）

Webフォームを使わず、既に`data/plan.json`に保存済みの内容でターミナルから一括実行することもできる
（「読込→シミュレーション実行（決定論的・感応度分析・モンテカルロ・ヒストリカルバックテスト）→
結果を`data/result.json`へ書き出す」を一括で行う）。

```bash
PYTHONPATH=. python3 scripts/run_full_simulation.py
```

モンテカルロ/ヒストリカルバックテストは計算に数十秒〜数分かかることがある。基本的な数値だけ
素早く確認したいときは省略できる:

```bash
PYTHONPATH=. python3 scripts/run_full_simulation.py --quick             # 両方省略して高速実行
PYTHONPATH=. python3 scripts/run_full_simulation.py --trials 1000       # モンテカルロの試行回数を指定（既定1000）
```

入力に不備があると処理を中断し、どのフィールドで何が問題かをターミナルに表示する
（`core/domain/errors.py`の`FireNavigatorError`）。この場合、`data/result.json`は
前回実行時の結果のまま更新されない。

### 入力項目（data/plan.json）

Webフォームの各セクションは`data/plan.json`の以下のキーにそのまま対応する
（`adapters/local/local_data_adapter.py`が読み込み・検証する）。

| セクション | JSONキー | 内容 | 必須 |
|---|---|---|---|
| 基本設定 | `user`・`assumptions`・`pension`・`life_expectancy_age`・`target_ending_networth` | 生年月日・インフレ率・年金条件（見込額・受給開始年齢）・想定寿命・目標資産 | 一部 |
| 口座 | `accounts` | 口座一覧（NISA/iDeCo等の口座種別・残高・保有資産クラス・期待リターン・取得原価） | ✓ |
| 収入 | `incomes` | 収入（開始/終了条件・年間金額・成長率） | ✓ |
| 支出 | `expenses` | 経常支出・単発支出（車・旅行・住宅購入等）を`kind: "recurring"/"one_time"`で区別 | ✓ |
| 配分方針 | `allocation_policy` | 年齢別の目標配分比率（資産クラス別、プラン全体で1つ、口座横断） | 任意 |
| 子供/教育費 | `children`・`education_expenses` | 子供の一覧（生年月日）と年齢帯別の教育費（小学校・塾・中学・高校・大学等、月額） | 任意 |

基本設定は旧ドラフトのMasterシート（主要条件をまとめて素早く変更できる単一ビュー）の方向性を
踏襲し、年金見込額・年金受給開始年齢・目標資産（想定寿命時点）も含めて1つのフォームセクションに
集約している（いずれも任意入力。未入力時は年金見込額ゼロ・標準65歳受給という後方互換の
デフォルトになる）。年金の繰上げ/繰下げによる増減率は「年金受給開始年齢」の数字だけから
自動的に決まる（早期/標準/繰下げの種別を別途選ぶ項目はない）。

シミュレーション期間は常に想定寿命（`life_expectancy_age`、未入力なら
`DEFAULT_LIFE_EXPECTANCY_AGE`(100歳)）まで計算する。給与収入等がいつ止まるかは収入の
終了条件タイプ/値で個別に設定する。

開始/終了条件タイプはフォーム上で`プラン開始時から`・`年齢で指定`・`日付で指定`の3択（内部的には
`core.domain.value_objects.EventConditionType`にマッピングされる）。開始/終了条件値は、
タイプが`年齢で指定`なら年齢の数字（例: 45）、`日付で指定`なら年月（例: 2027-06）を入力する。
終了条件タイプが未指定の行は「プランの最後まで継続する」という意味になる。

支出は単発フラグに相当する`kind`（`"recurring"`=経常支出／`"one_time"`=単発支出）で行の意味が
変わる。`recurring`の行は経常支出（年間金額・成長率、開始/終了条件も任意で使え、いつからいつまで
発生するかを指定できる。両方省略すればプラン全期間で発生する。途中で金額が変わる支出は、
開始/終了条件をずらした複数行に分けて表現する）、`one_time`の行は単発支出（単発金額と開始条件
タイプ/値で発生年月を指定する。単発支出には終了条件の概念はない）として扱う。両方の`kind`で
互いのフィールドを混在させることは許されず（局所的な警告ではなく即エラーで拒否する）、
教育費（`education_expenses`）は同じ子供IDの行すべてに同じ生年月日を`children`側で
一度だけ記入する。

`account_type`・`asset_class`等の値は内部識別子として英語のまま扱う。NISA/iDeCoは制度の正式名称
のため英語表記を維持する。

入力に不備があると`SchemaValidationError`が送出され（`core/domain/errors.py`）、フォーム上に
「どのフィールドで・何が」の形式でエラーメッセージが表示される（Sheets版にあった「警告のまま
実行を続ける」という緩い扱いは廃止し、構造的な不備は常に即エラーで拒否する設計にしている）。

### ダッシュボード

旧ドラフトのDashboardシート（1画面で主要指標を把握できる要約ビュー）を踏襲したKPIカード群。
`reports/dashboard_builder.py` の `build_dashboard()` が以下を算出する。

- 今年/今月使える追加金額（目標資産を下回らない範囲で生活費に上乗せできる金額を、
  既存の決定論的Projection Engineに対する二分探索で逆算する）
- 資産枯渇年齢（想定寿命までにnetworthが0以下になる最初の年齢）
- 目標資産との余裕（想定寿命時点の予測networth − 目標資産）

「今月使える金額」は現時点では年額を12等分した暫定値であり、Projection Engineの月次化後に
月次粒度の値へ置き換える予定（`docs/FIRE_Navigator_旧ドラフトとのギャップ分析_追加要件定義.md` 3.1）。

## 既知の制約

- 資産クラスは`config/asset_classes.yaml`で管理しており、コード変更なしに追加できる
  （`repositories/asset_class_repository.py`）。ただしMonte Carlo/Historical Engineで
  使うには別途`config/market_data/`に過去リターン系列を追加する必要があり、未追加の資産クラス
  （例: `btc`）はこれらのEngineの加重平均リターン計算で実質0%リターン扱いになる
  （決定論的なProjection Engineはこの制約を受けない）。
- `config/market_data/historical_returns_1928_2024.yaml`の過去リターン系列（S&P500・米国長期国債）
  はAswath Damodaran教授（NYU Stern）の公開データセットに基づく実データ（詳細はファイル内コメント参照）。
  1928年から収録しているのは、ヒストリカルバックテストが必要とする長期の窓（想定寿命までの
  60年前後）を過去データから作れるようにするため。
- `inflation_rate`（`assumptions`）は、収入/支出で成長率が未入力の行の既定値として
  使われる（入力済みの行はそちらを優先）。この解決は入力読込時（`adapters/local/
  local_data_adapter._parse_growth_rate`）に行われるため、感度分析でinflation_rateを仮に
  振っても、既に読み込み済みのIncome/Expenseの成長率には反映されない（感度分析のインフレ率軸は
  現状変化しない列のまま）。
- 譲渡税は課税口座（TAXABLE）からの取り崩し・リバランス売却時のみ対象。iDeCo等その他口座の
  出口課税（退職所得控除等）、譲渡損失の損益通算・繰越控除は対象外（ギャップ分析5.2/6章で確定した
  簡易化）。住宅ローン（`core/domain/loan.py`）も未実装。
- 資産配分の目標比率（`allocation_policy`）は口座ごとに1資産クラスのみを保有する前提（`accounts`の
  1件=1口座=1資産クラスという既存モデルに合わせた設計）。月次リバランスの再投資は各口座の
  拠出上限（年間/生涯枠）を尊重するが、通常の月次拠出フローとは別枠で判定する簡易化のため、
  両者を跨いだ年間枠の厳密な合算管理はしない（生涯枠は共有のlifetime_contributionsで正しく守られる）。
- Monte Carlo/Historical Engineの資産クラス別加重合成は、AllocationPolicy設定時はその時点の
  誕生日考慮の年齢（決定論的エンジンと同じ`age_at()`を使用）の目標配分比率を使う。ただし
  サンプリング対象の資産クラス一覧はシミュレーション開始時点(offset=0)の構成で決め打ちする
  （`_ever_weighted()`）ため、開始時点でまだどの目標配分比率も適用されない場合（例:
  AllocationPolicyの最小の年齢がプラン開始時点の年齢より高い場合）、対象の資産クラスが
  シミュレーション全体を通じて0件になり、その後年齢が上がって配分方針が適用されるようになっても
  反映されない可能性がある。同様に、途中の年齢で新しい資産クラスが初めて登場するケースも
  反映されない。
- 収入（`Income`の`start_condition`/`end_condition`）・経常支出（`Expense`の`start_condition`/
  `end_condition`、いずれも任意）は月精度で開始/終了を判定し、条件が年の途中で成立する年は
  該当月数分だけ按分計上する（`_active_months_in_year()`）。経常支出は両方省略すればこれまで通り
  プラン全期間で発生する扱いになり、途中で金額・成長率ごと変わる支出（保育料や住宅ローン完済後の
  生活費変動等）は開始/終了条件をずらした複数行に分けて表現する。単発支出（`kind: "one_time"`の行）は
  `resolve_condition_month()`により発生月を正確に判定する（Sprint14）。単発金額は「プラン開始時点
  （今日）の価値」として入力する前提で、発生年までプラン共通の`inflation_rate`で複利計算してから
  計上する（`_one_time_expenses_by_month_offset()`）。
- 教育費（`education_expenses`）の月額は「プラン開始時点（今日）の価値」として入力する前提で、発生する年
  までプラン共通の`inflation_rate`で複利計算してから計上する（`_education_expense_monthly_total()`、
  単発支出と同じ考え方）。教育費バンドの年齢帯（開始年齢〜終了年齢を含む）は、子供の誕生月ではなく
  学年（4月1日時点の年齢）を基準に切り替わる（`_school_year_age()`）。
- 年齢は`AgeAt`により誕生日を考慮して毎月再計算する（`_age_at()`）。配分方針の年齢帯判定・
  `YearlyProjection`/`MonthlyProjection.age_self`に反映される。公的年金は受給資格年齢に達する年を
  誕生日基準の月数で按分計上する（`_pension_income_for_year()`）ため、例えば4月生まれで65歳受給の
  場合、65歳になる年は4〜12月の9ヶ月分のみ計上される。
- 年次ループの区切り（所得税・住民税・社会保険料等を年1回計算する単位）は、プラン開始月ではなく
  「年齢が実際に切り替わる月（誕生月の翌月。誕生日が1日の場合は誕生月そのもの）」を起点にしている
  （`_age_transition_month()`）。これにより年齢条件（`年齢で指定`）による収入・支出の開始/終了が
  区切りの境界とちょうど一致し、月次の按分がずれない。最初の区切りだけプラン開始月から直後の
  年齢切り替え月の前月までの可変長（1〜12ヶ月）になり、シミュレーション期間全体としては
  想定寿命に到達する年齢までは変わらないが、区切りが暦年とずれる関係で、到達する
  西暦年が従来の単純計算（誕生年+年齢）より1年ずれ込むことがある（許容する）。日付（YYYY-MM）に
  よる開始/終了条件は誕生日と無関係なため、この区切りの途中でまたがるケースは残る（許容する）。
- 所得税・住民税・社会保険料は年1回の確定計算のみで、その結果をその区切りの実際の月数で割って
  毎月のキャッシュフローに反映する（月ごとの累進課税の再計算はしない。日本の税制がそもそも
  年次確定であるため）。公的年金等控除は
  2020年分以降の速算表（65歳未満/65歳以上で異なる表）を実装している（`config/tax_2026.yaml`の
  `pension_deduction_under_65`/`pension_deduction_65_or_older`）。65歳未満/以上の判定はその年の
  年末時点の年齢（`_age_at()`）で行う。公的年金等以外の所得が1,000万円を超える場合の控除縮小には
  対応しない（MVP簡略化）。
- 住民税の均等割（`per_capita_levy`）は、収入が全くない場合は非課税とするが、収入はあるが各種控除で
  課税所得が0円になった場合は課税する（実際の非課税限度額判定を厳密に再現するものではない）。
  社会保険料（健康保険・厚生年金）は標準報酬月額上限相当の年収換算キャップを設定している
  （`config/tax_2026.yaml`の`health_insurance_cap`/`pension_insurance_cap`。等級表そのものは未実装の概算値）。
- 決定論的シミュレーション（`run_projection`）は口座ごとの期待リターン（`accounts`の期待リターン、
  必須項目）で各口座を個別に成長させる。プラン全体の投資成長率という設定項目は持たない（口座に
  紐づくポートフォリオ情報がない場合のフォールバック、および未割当余剰資金（unallocated_surplus）の
  成長率はいずれもゼロ成長として扱う）。感応度分析の成長率軸は、この
  各口座の期待リターンに一律で増減幅（-1%/±0%/+1%）を加える形で振る。Monte Carlo/Historical
  Engineは従来通り、過去実績データの資産クラス別分布を`allocation_policy`の資産クラス比率で加重合成した
  単一レートを全口座に一律適用する設計のままで、口座ごとの期待リターンは使わない（相関構造を
  重視するため）。
- Historical Engineの月次バックテストは、実際の年次リターン実績値を`monthly_equivalent()`で月率換算し
  同じ年の12ヶ月に均等適用する近似（実際の月次指数データへの置き換えは将来課題）。
- Monte Carlo Engineは毎月新規に相関考慮サンプリングするため、月次化により1試行あたりの計算量が
  約12倍に増えている（trials=1000・想定寿命までの長期プランで実行に1分弱かかる場合がある）。
